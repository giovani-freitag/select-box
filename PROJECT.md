# select-box — multi-framework Combobox library

Pilot project to validate a TanStack-style framework architecture:
**framework-agnostic core** plus thin wrappers for every popular UI
framework. The combobox extracted from `the-origin-app` is the first
component; the conventions and tooling established here become the
template for future components.

## 1. Goals

1. **One source of truth** for state, search, filtering, virtualization,
   keyboard nav. No framework-specific logic in the core.
2. **Same public API across wrappers** — `useSelectBox` / `createSelectBox`
   / `injectSelectBox` / `$.fn.selectBox` all take the same options shape
   and surface the same snapshot/methods (TanStack convention).
3. **Matrix E2E** — a single behavioural test suite runs against every
   framework's example app. A core regression is caught by the same
   assertion in every wrapper, so cross-framework drift is impossible.
4. **Modern stack only** — latest stable React, Vue, Lit, etc. No back-
   support shims unless the framework itself ships them.
5. **Live, editable docs** — VitePress + TypeDoc + WebContainers iframe
   per framework, with a framework switcher.

Non-goals: server-side rendering compatibility (would be nice; deferred);
internationalisation (consumer concern); accessibility audit beyond WAI-
ARIA combobox spec (covered by core + tests).

## 4. Core architecture

### 4.1 Pattern

**Observer / external store.** Every controller exposes:

```ts
class SingleSelectBoxController<TValue> {
    constructor(config: SingleSelectBoxConfig<TValue>);

    getState(): SelectBoxSnapshot<TValue>;
    subscribe(listener: () => void): () => void;   // returns unsubscribe

    // Mutations — all sync, fire listeners after state change
    open(): void;
    close(): void;
    setQuery(query: string): void;
    moveActive(delta: number): void;
    commitActive(): void;
    commitOption(option: SelectOption<TValue>): void;
    clear(): void;
    destroy(): void;
}
```

This is the same shape React's `useSyncExternalStore` consumes, what
Vue's `customRef`/`watchEffect` bridges, what Lit's `ReactiveController`
plugs into, and what the web-components wrapper triggers via
`requestUpdate()`. No framework-specific concession in the core.

### 4.2 Class design rules (apply to every controller)

Follow the existing repo conventions (see `feedback_class_design.md` in
the consumer's notes for context):

- Constructor takes **one** typed config object (`<ClassName>Config`).
- `>3` positional params → already an options object; no exceptions.
- Booleans are never positional.
- Collaborators (filter strategy, virtualizer) injected via the config —
  never `new`'d inside.
- Fields private by default; expose state via `getState()`.
- Errors are thrown (no `Result<T,E>`).
- Public methods/classes get a docblock so IDEs surface the contract.
- Setup that needs I/O / async / DOM access lives in an explicit
  `init()` / `attach(element)` method, **not** the constructor (two-
  phase initialization). `destroy()` pairs it.

### 4.3 Reactivity contract

- `subscribe(listener)` calls `listener` on **any** state mutation.
- `listener` is invoked synchronously after the mutation finishes.
- `getState()` returns a **stable reference** when nothing changed —
  wrappers can use referential equality to skip re-renders.
- Listeners must be idempotent and side-effect-free w.r.t. the
  controller (no calls back into mutators inside a listener — could
  cause reentrancy bugs; documented warning).

### 4.4 Naming

- Identifiers full words, no abbreviations.
- Public methods/functions read as a phrase (`moveActive`, not `mvAct`).
- Loop counters are the only allowed shorthand.

### 4.5 Option groups

Native `<optgroup>` parity. Options can be supplied flat or nested:

```ts
type SelectOption<TValue> = {
    value: TValue;
    label: string;
    disabled?: boolean;
    /** Optional group key — leaf options that share a key get grouped under it. */
    group?: string;
};

type SelectGroup<TValue> = {
    key: string;
    label: string;
    disabled?: boolean;
    options: SelectOption<TValue>[];
};

type SelectBoxConfig<TValue> = {
    options?: SelectOption<TValue>[];          // flat with optional `group` field
    groups?: SelectGroup<TValue>[];            // pre-grouped
    // …
};
```

Rules:

- The controller normalises both inputs into an internal **ordered list of
  groups**. A flat `options` array without `group` fields collapses to a
  single anonymous group rendered without a header.
- Filtering runs across leaves but the snapshot exposes
  `filteredGroups: SelectGroup<TValue>[]` so wrappers render headers.
  Empty groups are dropped from the snapshot.
- Keyboard navigation skips group headers and disabled options.
- The virtualizer treats group headers as fixed-size rows interleaved with
  option rows; row index ↔ (group, option) mapping lives in core.
- Sticky group headers during scroll are a wrapper concern (CSS), not
  core.

### 4.6 Extension model (addons)

Selectize-style `.use(addon)` pattern. Addons attach to a controller and
extend behaviour without bloating the core.

```ts
interface SelectBoxAddon<TValue> {
    readonly name: string;
    // Two-phase setup: constructor stores config only; attach() allocates
    // the addon's own state slice and is paired with detach().
    attach(initialSnapshot: SelectBoxSnapshot<TValue>): void;
    detach(): void;
    // Optional pure-transformer hooks (see table below). The core calls
    // whichever the addon declares; the addon never receives a mutable
    // controller reference.
    transformGroups?(groups, ctx): ReadonlyArray<SelectGroup<TValue>>;
    transformOptions?(options, group, ctx): ReadonlyArray<SelectOption<TValue>>;
    interceptCommit?(option, ctx): SelectOption<TValue> | null;
    interceptOpen?(ctx): boolean | Promise<boolean>;
    interceptClose?(ctx): boolean | Promise<boolean>;
    extendSnapshot?(snapshot, ctx): unknown;
    onKeyDown?(event, ctx): "handled" | "pass";
}

class HoistSelectedAddon<TValue> implements SelectBoxAddon<TValue> { /* … */ }

controller
    .use(new HoistSelectedAddon({ separator: true }))                          // when: "always" by default
    .use(new CreateOptionAddon({ allowCreate: (query) => ({ value: query, label: query }) }));
```

**Hook surface** — every hook is a **pure transformer** of read-only
data. Hooks never receive a mutable controller reference, so an addon
**cannot** trigger a state mutation from inside a hook. This is the same
design TanStack Table uses for `getSortedRowModel` / `getFilteredRowModel`
and it makes reentrancy structurally impossible.

| Hook | Signature (simplified) | Purpose |
|---|---|---|
| `transformGroups` | `(groups, ctx) => groups` | Reorder, inject, hide groups (used by hoist) |
| `transformOptions` | `(options, group, ctx) => options` | Reorder/inject within a group |
| `interceptCommit` | `(option, ctx) => option \| null` | Replace (return new) or veto (return `null`) a commit |
| `interceptOpen` / `interceptClose` | `(ctx) => boolean \| Promise<boolean>` | Async gate (e.g. load options before open) |
| `extendSnapshot` | `(snapshot, ctx) => addonState` | Return the slice to publish under `snapshot.addons[name]` |
| `onKeyDown` | `(event, ctx) => "handled" \| "pass"` | Custom shortcut without mutating during the call |

**Rules**:

- `use()` returns the controller (chainable). Calling `use()` after
  `init()` is allowed; the addon's `attach()` runs immediately.
- Addons follow the same class-design conventions as controllers:
  single typed config object, `<AddonName>Config`, no I/O in constructor,
  `attach`/`detach` is the two-phase boundary.
- Hooks are **pure transformers** — they receive immutable inputs and a
  read-only `ctx` (snapshot fields + addon's own state slice) and return
  new data. The core applies the return value. No reentrancy guards
  needed because no hook holds a mutable handle.
- The order of `use()` calls is the order hooks fire. Documented and
  asserted in tests.
- Snapshot extension is **typed via declaration merging**, same as
  TanStack Table. Each addon ships a `module.d.ts` augmenting
  `SelectBoxAddonSnapshots` so `snapshot.addons["hoist-selected"]` is
  typed without casts — installing the addon package brings the types
  along.
- Addons ship as their own packages under `packages/addon-<name>/` so
  consumers tree-shake what they don't use. **Nothing is bundled in the
  core by default** — every behaviour beyond bare single/multi commit
  is an opt-in install.

**First-party addons** (separate packages, none auto-loaded). Status
key: `[done]` implemented · `[wip]` spec'd or scaffolded, not finished ·
`[plan]` planned, no design yet.

- `[wip]` `@select-box/addon-clear-button` — clear-selection affordance. The
  default wrappers (`<SelectBox />`, `<select-box>`) render an `×` next
  to the trigger value when the addon is installed and there is a
  selection. Config: `{ label?: string; ariaLabel?: string }`. Exposes
  `snapshot.addons["clear-button"]: { visible, label, ariaLabel }`.
  Implementation lives at [packages/addon-clear-button/](packages/addon-clear-button/);
  re-wire the example once the ready `<SelectBox />` component lands.
- `[plan]` `@select-box/addon-inline-search` — Selectize-style "search input
  *is* the trigger". When installed, the trigger renders a text input
  in place of the static label; focusing it puts the controller into
  search mode and shows the popover; the placeholder swaps for the
  selected option's label when blurred. Hook surface needed:
  `extendSnapshot` (for `inputMode: "label" | "search"`) and
  `onKeyDown` (for the typing experience). Config:
  `{ keepQueryOnBlur?: boolean }`.
- `[wip]` `@select-box/addon-hoist-selected` — pins selected options to the top
  of the list. Always active while there is at least one selection.
  Order of pinned items matches the order of the controller's `value`
  array (stable; the consumer decides via selection order). Config:
  `{ separator?: boolean; when?: "always" | "popoverOpen" }`,
  default `when: "always"`. Exposes
  `snapshot.addons["hoist-selected"].pinnedKeys`. Requires the
  `transformGroups` hook (not yet wired in core).
- `[plan]` `@select-box/addon-create-option` — adds an "Add `<query>`" row
  when the query has no match. Requires `interceptCommit` + a snapshot
  flag for the synthetic row.
- `[plan]` `@select-box/addon-remove-button` — per-row remove affordance for
  multi mode (chip-list trigger). Activates with the multi-mode
  milestone (M2).
- `[plan]` `@select-box/addon-restore-on-backspace` — selectize parity:
  Backspace on empty query in multi mode pops the last chip back into
  the input as editable text. Requires `onKeyDown` + `interceptCommit`.
- `[plan]` `@select-box/addon-persist` — saves/restores selection to
  `localStorage` (wrapped behind a `StorageService`, per service-layer
  pattern). Config: `{ key: string; storage?: "local" | "session" }`.

## 5. Wrapper consistency

Every wrapper exports an API named after the framework's idiomatic
factory but with the **same signature and snapshot fields**:

| Framework | Entry | Returns |
|---|---|---|
| Vanilla / Web Components | `<select-box options="…" mode="single">` + DOM events | Element with `.controller` getter |
| React | `const { state, controller } = useSelectBox(config)` | Snapshot + controller methods |
| Vue | `const { state, controller } = useSelectBox(config)` | Reactive refs + methods |
| Lit | `class extends LitElement { selectBox = new SelectBoxController(this, config) }` | Lit-reactive |
| jQuery | `$('selector').selectBox(config)` chain + `.selectBox('controller')` | jQuery collection |

Snapshot field names (`open`, `value`, `query`, `filtered`,
`selectedOptions`, `activeIndex`, `isEmpty`) are identical across every
wrapper. **Tests assert on these field names directly.**

## 6. Testing strategy

### 6.1 Unit (in `packages/core/tests`)

- Pure controller tests. No DOM. Vitest, `expect` only (no chai).
- AAA pattern, blank-line separated (no `// arrange / // act / //
  assert` comments).

### 6.2 Per-wrapper integration

- Each wrapper has its own `tests/` folder with the minimal harness
  needed to mount it (jsdom for React/Vue, happy-dom for web
  components, etc.).
- Asserts the wrapper correctly subscribes/unsubscribes and renders the
  snapshot fields.

### 6.3 Matrix E2E (the headline feature)

- Single `e2e/specs/*.spec.ts` suite written against framework-agnostic
  data-test attributes (`[data-select-trigger]`, `[data-select-option]`,
  `[data-select-active]`).
- `examples/*` apps render the same scenarios in their respective
  frameworks, all using the canonical data-test attributes.
- Playwright's `projects` config runs the suite N times — once per
  framework — by spawning each example's dev server.
- A core regression fails the matrix in every framework simultaneously;
  a wrapper-specific regression fails only its column. The output
  diagnoses the layer immediately.

```
                 ┌─ wc ────── ✔ 42/42
                 ├─ react ─── ✔ 42/42
spec/keyboard ───┼─ vue ───── ✔ 42/42
                 ├─ lit ───── ✔ 42/42
                 └─ jquery ── ✗ 41/42   ← regression scoped to jquery only
```

## 8. Pilot: combobox feature scope

Full parity with `src/renderer/src/components/ui/selector/combobox.tsx`
from `the-origin-app`. Concretely:

- Single + Multi mode (discriminated by config).
- Popover trigger UI (search input + virtualized list).
- Inline chip UI (no popover, all options as toggleable chips).
- Fuzzy match filtering (default; pluggable).
- Virtualized list rendering for long option sets.
- **Option groups** (`<optgroup>` parity) — flat-with-`group` or nested
  `groups` input shape; filtered snapshot exposes `filteredGroups`;
  keyboard nav skips headers/disabled.
- Keyboard navigation: ArrowDown/Up, Enter, Escape, Tab, Backspace.
- Clear-all and per-tag remove (multi only).
- Controlled `value` + `onValueChange` props (RHF-friendly).
- **Addon system** (`.use(new Addon(config))`) wired in the core from
  day one. Hoist-selected ships as the reference first-party addon
  exercised by the matrix E2E.

The internal split mirrors the existing controllers (`SingleComboboxController`,
`MultiComboboxController`) but lifts every DOM reference out — the
controllers now operate purely on snapshots and options.

## 10. Open risks

1. **WebContainers cold-start latency** — Vue/Lit examples may take a
   few seconds to boot the WebContainer. Mitigation: lazy mount only on
   user interaction with the framework switcher; show static screenshot
   placeholder before.
2. **jQuery wrapper architecture stress** — jQuery is imperative; users
   expect chainable API + plugin pattern. May force concessions in how
   options are passed (object vs `data-*` attrs) and how teardown works
   (no automatic lifecycle). Plan: design jquery wrapper LAST in M1 so
   we adjust the core only after the other four wrappers stabilise.
3. **Virtualizer cross-framework** — TanStack Virtual ships React/Vue/
   Solid adapters; for web components/jquery/lit we'd reimplement the
   row math. Alternative: write a tiny framework-agnostic virtualizer
   in core and skip the dep. Decision deferred to M1 spike.
4. **Matrix CI minutes cost** — 5 frameworks × 2 browsers × N specs
   gets expensive. Mitigation: only run full matrix on PRs that touch
   `packages/core` or `e2e/`; per-wrapper changes only run that
   wrapper's column.

## 11. Conventions inherited from the consumer (the-origin-app)

These rules apply by default; deviations need a comment:

- **Meaningful naming**: no abbreviations; identifiers read as a phrase.
  Loop counters and well-established acronyms (DOM, HTML) are the only
  exceptions.
- **Class design**: single typed config object as constructor arg;
  collaborators injected; explicit return types on public methods.
- **Two-phase initialization**: classes that touch DOM/listeners/I/O
  split constructor (config-only) from `init`/`attach`/`destroy`.
- **Service-layer pattern**: third-party I/O libs wrapped behind a
  `*Service` in `services/<domain>/<domain>-service.ts`. For this lib
  the only candidate is the StackBlitz SDK in the docs — wrap it before
  importing.
- **Comment discipline**: English only; public surfaces get docblocks;
  inline comments explain non-obvious *why*, never restate code.
- **Flat method bodies**: extract closures to named methods; event
  controllers use paired `listen()`/`unlisten()` with stable refs from
  `bindMethods()`.
