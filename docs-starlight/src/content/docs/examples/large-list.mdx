The control below regenerates a unique cartesian product of three
hand-curated word lists — `adjective × animal × profession` — and feeds the
result into all five framework demos through a shared `window.__bigListSeed`.
Slider is geometric: drag to **10 000** items and the popover still opens
instantly because only the ~7 rows inside the visible window touch the DOM.
Push it to **500 000** and notice the search input still filters in real time.

## Why this works at 500 000 items

- The list is rendered through `ListVirtualizer` — only rows whose pixel range
  intersects the viewport are appended to the DOM. With a 240 px popover and
  36 px rows that's ~7 rendered nodes at any time, regardless of the source size.
- The filter (`SubstringFilterStrategy` here, but you can plug
  [`FuzzyFilterStrategy`](/examples/search/)) walks the array linearly. For
  500 000 short strings on a modern laptop that's ≈10–30 ms per keystroke —
  the search input stays interactive without throttling.
- Generation itself takes the dominant time (~100 ms for 100 000 items,
  ~700 ms for 500 000). The page defers it to `requestAnimationFrame` so the
  slider readout paints first.

## Caveats

- Keyboard `↓` past the visible window scrolls the active row into view via
  `controller.getState().activeOption` + the virtualizer's `getOffset(index)`.
  At 500 000 rows that's instant.
- The slider here uses a **geometric** scale (`10 → 500 000`) because a
  linear one would spend 99 % of its travel on counts above 50 000.
- `window.__bigListSeed` is intentionally a single shared array — every
  framework demo reads from the same reference, so we pay the generation cost
  once even though five islands render the list.
